## 4. 缺陷清单

> 自动化用例 **0 失败**。以下 3 条均为**潜在健壮性**问题（P2），**未在本机复现**，不影响功能验收，建议后续加固。

### P2-1 相机读帧阻塞时 `Close()` 可能长时间挂起
- **文件:行**：`src/VisionPlatform/Camera/LocalCamera.cs:106-122`、`src/VisionAlgo.Native/src/algo/algo_camera.cpp:113-127, 174-189`
- **现象**：`StopGrab()` 仅 `Join(1000)`；若采集线程仍阻塞在 `cv::VideoCapture::read`（C++ 侧 `CameraGrab` 持 `cam->mtx` 跨整个 read，且 `read` 本身无超时，代码亦注释承认），则随后 `CameraClose` 会阻塞在 `cam->mtx` 上，导致关闭操作用户感知为卡死。
- **复现**：需异常/掉线相机（本机设备读帧正常，未触发）。
- **建议修复**：为设备异常路径提供看门狗（如超时后放弃 Join 并标记句柄延迟释放），或改用以超时方式读帧的后端封装。

### P2-2 采集线程无节流 + 异步 `BeginInvoke`，UI 慢时帧积压
- **文件:行**：`src/VisionPlatform/Camera/LocalCamera.cs:229-304`、`src/VisionPlatform/UI/CameraForm.cs:158-178`
- **现象**：`GrabLoop` 无输出节流（对比 `SimCamera.GrabLoop` 有 `Thread.Sleep(100)`），且 `FrameReceived` 走异步 `BeginInvoke`；当 UI 渲染慢于采集速率时，消息队列会积压大量 `Bitmap`，短时内存上涨。
- **复现**：高帧率相机 + 慢机器/慢渲染时可观察到（本机未长时间压测）。
- **建议修复**：`GrabLoop` 增加最小帧间隔，或 `OnFrame` 采用「覆盖式」投递（仅保留最新帧）。

### P2-3 `FlowForm.OnFormClosing` 未等待运行线程即释放算法上下文
- **文件:行**：`src/VisionPlatform/UI/FlowForm.cs:571-580`（关闭）与 `:477-504`（运行线程）
- **现象**：运行中关闭编排窗体时，`_runner.Dispose()`（内部 `_algo.Dispose()` 释放原生 Context）与运行线程中的 `_runner.Run()`（可能正调用原生算法）存在极小概率并发，理论上可致原生层访问已释放句柄。
- **复现**：单帧运行通常在数十 ms 内完成，窗口极窄，未复现。
- **建议修复**：关闭时先等待/取消运行线程（`Join`）再 `Dispose`，或为 `Run` 与 `Dispose` 加互斥。

## 6. 智能路由判定

### 判定：**NoOne**（全部自动化项通过）

**理由**：
- ① 原生相机链路 **20/20 用例通过**（枚举=1、打开、640×480、连续 3 帧、错误路径不崩溃、帧内容为逐帧变化的活流）——**功能可用**；
- ② 错误/边界路径全部返回预期错误码且**无崩溃**（`enum(NULL)`、`open(99)`、`grab(NULL)`、`close(NULL)`、错误通道、尺寸不匹配）；
- ③ 既有形状匹配算法回归通过（训练 128 特征点、匹配得分 1.000）——**新增相机代码未污染既有导出**；
- ④ Debug/Release **强制全量重编译均成功**，无新增告警；
- ⑤ 12/12 新增文件登记齐全；
- ⑥ 6 个关键风险点静态核查全部符合设计铁律（Bitmap 所有权、退订顺序、Flows 补齐、越界保护、Stride）。

**关于第 4 节 3 条 P2 缺陷**：均为**潜在健壮性问题、未复现故障、不影响功能验收**，故不转 Engineer 作为「源码 Bug」处置；建议作为**后续加固项**知会工程师。
**关于第 5 节**：WinForms 交互与实时画面属**能力边界外的不可自动测项**，已如实列为人工验证清单，**不作为失败项**。

## 7.2 本轮新增缺陷清单

### P2-4（③）StopGrab 超时后立即 StartGrab 的采集线程状态竞态
- **文件:行**：`src/VisionPlatform/Camera/LocalCamera.cs:341-345`（GrabLoop 退出统一清 `_thread/_grabbing`）、`:166-182`（StopGrab 超时不清理 `_thread`）、`:149-164`（StartGrab 仅以 `_grabbing` 防重入）
- **现象**：设备读帧阻塞导致 `StopGrab` 超时（`Join(1000)` 返回 false，`:177-180`）后 `_grabbing` 已置 false；此时用户若立刻「开始采集」，会创建**新线程**并覆盖 `_thread`。旧线程随后退出时会执行 `lock(_sync){ _grabbing=false; _thread=null; }`，**误清新线程的 `_thread` 引用并把 `_grabbing` 误置 false** → `IsGrabbing` 误报、`Close` 可能不再等待新线程。
- **复现前提**：相机读帧阻塞 >1s（丢线/假死设备）+ 停机后 1s 内再次启动（本机未复现）。
- **缓解现状**：C++ 侧 `CameraGrab`/`CameraClose` 由 `cam->mtx` 串行化，且 `Close` 先把 `_handle` 置零使新线程下一轮 `:271` 检测到空句柄而退出 → **不崩溃、不悬垂**，仅状态误报 + Close 语义弱化。
- **建议修复**：为每次 StartGrab 分配 generation/token，GrabLoop 退出时**仅当 `_thread` 仍指向本线程**才清空；或 StartGrab 在旧线程存活时拒绝启动。

### P2-5（⑤）FlowForm 运行收尾委托缺少 `IsDisposed` 防护
- **文件:行**：`src/VisionPlatform/UI/FlowForm.cs:489-505`
- **现象**：运行在关窗后 ≤2s 内结束时（`Join(2000)` 成功，`_closeWhenIdle` 保持 false），该收尾 `BeginInvoke` 委托可能在对已释放窗体执行 `btnRun.Enabled=...` / `SetStatus(...)`（多半为良性空操作，但非防御式写法）。
- **建议修复**：委托开头加 `if (IsDisposed || !IsHandleCreated) return;`。
- **相关 trade-off（非缺陷，已接受）**：若 `_runner.Run` 永久挂起（如相机假死），`e.Cancel=true` 循环会使 FlowForm **无法关闭**；单帧 Run 有取帧上限，实践可接受，此处仅记录。
