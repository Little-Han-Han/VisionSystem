## 1. 摄像头接入与流程编排

### 1.1 目标

- **问题**：现场调试时，用户可能既没有海康工业相机，也不方便用合成图像调参；笔记本内置摄像头 / 普通 USB 摄像头随手可得，但系统当前无法枚举、打开它们。
- **目标用户场景**：
- 现场工程师在无工业相机环境下，用本机摄像头做算法取图与联调预览。
- 售前/演示场景，快速展示"实时采集 → 检测"的完整链路，无需携带工业相机。
- **目标**：
- **G1**：能枚举出本机（USB / 内置）摄像头，并在相机管理界面**打开**。
- **G2**：打开后可**连续采集并实时显示**（预览流畅、可停止）。
- **G3**：无任何真实硬件时**合理降级**到现有 SimCamera，界面不报错、不阻断流程。
- **问题**：当前算法页是"一页固定参数"，只能跑形状匹配一条固定链路，无法表达"取图 → 若干算法模块 → 结果输出"的可配置流程，也无法与主界面显示窗口 / 相机建立绑定关系。
- 工程师参考 VisionMaster 的操作习惯，用**拖拽 + 连线**方式搭建处理流程。

## 2. 界面布局与算法模块

### 2.1 目标

- **一句话目标**：把 VisionSystem 主界面改造成"一眼可读"的工业 HMI（良品率 / OK-NG / 运行控制成为视觉焦点），同时把流程编排补齐为覆盖「取图 → 定位 → 位置修正 → 检测/量测 → 判定」的完整算法工具链，并让**每个节点的中间处理效果在流程界面内实时可见**。
- 多分支 / 并行流程拓扑（仍为**单链**）；
- 海康真实相机 SDK 联调；
- 视觉标定（像素当量 / 手眼标定）；
- 图标资源、皮肤换肤系统、第三方 UI 库。

## 3. 多相机 · 多产品 · 流程并行

### 3.1 目标

- **一句话目标**：让 VisionSystem 从"一次跑一条流程的单工位工具"升级为"一套软件同时管理**多个相机、多个产品、多条并行流程**，且每条流程在界面上**可分辨、可追溯**"。
- **单流程内部分支并行**（方案②）：需重写拓扑解析与 ROI/变换作用域，与既有单链约束冲突，本期不做（见 §6 冲突点 C-1）；
- 相机硬件同步触发（外触发 / 编码器同步）；
- 跨流程的结果关联（如"相机 A 定位结果传给相机 B 的流程"）；
- 分布式 / 多机部署。

## 4. 模板制作与 OCR 旋转 ROI

### 4.1 目标

- 1. **让"做模板"成为一件用户能看见、能确认、能长期复用的事**：现在的模板制作是不可见的（点按钮没反应、成功与否无反馈）且不持久的（只活在内存里，重启即失，必须靠跑一次流程"隐式示教"），产线每次换型开机都要重做一遍，这是纯粹的无效工时。
- 2. **让 OCR 能只认该认的那块区域，并且认得正**：现在 OCR 只能识别整帧、ROI 永远是轴对齐的矩形，工件一旦在视野里转了一个角度，字符就跟着歪，切分和识别准确率直接掉下来。
- 3. **补上"旋转矩形"这个系统级缺失的输入能力**：让带方向的矩形从"只能显示"变成"可以作为参数输入"，后续其他节点（Blob、缺陷检测）都能复用。

### 4.2 需求清单

### 4.3 验收口径与硬约束

- **老流程配置必须能直接跑**：升级前的流程配置/配方里不存在任何新增字段，加载后必须正常工作，且**不得要求用户重新配置或重新制作已有模板**。缺失字段一律取"无 ROI / 关闭跟随"的等价语义，绝不允许因字段缺失抛异常或把节点置为失效。
- **老行为不得劣化**：未配置 ROI 的 OCR 节点输出必须与升级前逐像素一致（仍是整帧识别）；**轴对齐 ROI（`RoiAngle=0`）且上游无坐标变换时，OCR 节点实际输入算法的灰度图也必须与升级前逐像素一致** —— 新实现刻意保留老的整数裁剪路径，两版本执行的是同一段代码，所以这条能成立、也必须成立；轴对齐 ROI（仅 X/Y/宽/高）必须仍然可用，角度默认 0。
- 说明：这条是**兼容性回归断言**，与 FR-10 (b) 是两件事 —— 后者比的是"内容等价"，因为扶正路径必然经过重采样，逐像素不可达（见 4.2 表后备注注 1）。
- **配置保存不得丢字段**：旧版本软件读新配置后另存，不得抹掉新增字段（前向兼容受版本能力限制，但至少不能静默清空）。
- **模板缺失不能阻断流程**：某节点模板文件丢失/损坏时，该节点给出明确提示，流程其余节点继续执行，不允许整条流程崩掉。
- 所有失败路径必须给出**中文 + 可定位**的信息：节点名、流程名、模板文件路径、具体原因。禁止只弹"操作失败"、禁止只写日志不提示界面。
- **训练超时门限 = 3000 毫秒**：从发起训练开始计时，超过 3000 ms 即判定为「训练超时」并中止，界面给出「训练超时（超过 3000 ms），请缩小 ROI 或降低金字塔层级后重试」。不允许无限等待，也不允许界面在此期间无响应。
- 模板相关的三类失败必须能区分：**文件不存在** / **文件损坏或版本不兼容** / **模板参数与当前节点设置不匹配**。三种在界面上提示文案不同。
- OCR 的 ROI 生效情况应可在日志/节点结果中查到（本次实际使用的 ROI 位置、尺寸、角度，以及角度来源是"手工配置"还是"跟随位置修正 θ=xx°"），便于现场排查"为什么 ROI 没跟着转"。
- 日志需包含：模板保存/加载的时间戳与路径；训练输入参数与结果分数；矫正后图像尺寸。
- **一条流程里只建议放一个形状匹配节点。** 如果同一条流程里放了**多个形状匹配节点**，因为算法库当前只有一个形状模型槽位，每帧都要为每个节点重新训练一次模型（每次约 60~300 毫秒），表现就是画面卡顿、掉帧、检测节拍变慢。系统会在**流程校验时给出警告**（只警告，不阻止运行）。建议一条流程只放一个形状匹配节点；工艺上确实需要多个的，请拆成多条流程。彻底解决需要单独排期改造算法库。
- 这条限制**不影响做模板这件事**：模板照常可以保存、重启后照常自动加载，只是运行时每帧要重训一次。**单节点流程本身是"训练一次、后续不重训"**（执行器每个窗体只构造一次、模型缓存常驻），不受影响。
- 根治办法是改造原生算法库做**模型池**，已单列为 P1 独立需求，不在本 PRD 交付范围。本期用"**流程校验期警告 + 运行摘要里显示重训耗时**"把这个限制显式化，让用户看得见、而不是靠猜。

→ 通用约定（坐标系、端子、主题、权限、日志等）见 [知识图谱 §2](../README.md) 与 [增量架构设计 §7](../架构/增量架构设计.md#arch-common)，此处不复述。

## 5. OCR 字符模板与结果呈现

### 5.1 目标

- 1. **把"做字符模板"从一个"必须先知道 exe 在哪、还要按规则改文件名"的隐性知识，变成界面上看得见、点得到、能当场验证的操作**——现状是目录为空、界面无入口、失败无提示，用户只会得到一个结论："这软件不认字"。
- 2. **让"结果"在工程师需要判断的那一秒就能被读懂**：右栏总高 637 px 里参数区只剩 185 px、结果表 7 列挤在 288 px 里必须横向拖、匹配分数和 Blob 面积这两个最关键的数在界面上根本显示不出来——这不是"不够好看"，是**关键判据不可读**。
- 3. **消除三处"静默"**：空模板库静默跑成 OK、坏模板图静默跳过、切换节点静默清空结果。三处都会让用户误判"功能坏了"或"检测通过了"。

### 5.3 验收口径与硬约束

- **适用范围（v1.5 收窄）：这一条不是"任何节点点了都必须高亮"，而是"点开过的节点必须高亮"。**
- **为什么这样界定（写进文档，防止以后被当成"实现偷懒"改回去）**：
- **缩略帧是按需生成的，不是每帧给所有节点都降采样。** 原因是性能硬约束：5 个节点每周期各做一次 5MP → 1/4 缩放约需 5~15 ms，会直接顶破 **16 ms** 的刷新预算（见 §5.3）。
- 因此"从未被点开过的节点没有缩略图"是**设计的必然结果，不是能力缺失**。
- **这不是降级，是把适用范围写准。** 若不写清，后果有两个，且第二个更糟：① QA 会在"从未点开"的场景按 C5 原字面测，判我们不通过；② 有人为了"修好验收"把按需生成改回"每帧全量降采样"，性能掉下来还以为是修好了 —— 这是拿 16 ms 预算换一条本来就不该存在的断言。
- "点行高亮预览"是现网唯一的"结果 → 图"定位手段，**改版必须保留且只能增强**（见 C5 / §5.1.1 四条断言）。明细行是新增的目标级入口，主行保留原有"选节点 + 高亮首个目标"语义。
- 结果区不得出现"空表格"：三种状态必须可区分 —— **尚未运行**（灰字文案）/ **运行中**（进度感 + 上次结果淡显）/ **已有结果**（数值 + 时间戳）。切换节点时**不得**先清空再回填（视觉跳动），应直接替换为缓存内容。
- OCR 模板状态卡片沿用匹配类节点已建立的范式（就绪 / 未配置 / 失败 + 缩略图 + 数量 + 时间 + 重做/删除），**不新造一套视觉语言**。
- 模板侧三类失败必须**文案可区分且可行动**：目录不存在（→ 提供"创建目录"）/ 目录不可写（→ 提供"迁移"）/ 部分文件读取失败（→ 列出文件名 + 原因 + 可复制）。
- 禁止再次出现"静默吞掉"：任何一张模板图读取失败都必须计入"失败计数"并在界面某处可见。
- 结果侧必须能查到"这个数是哪个节点的第几个目标、哪一帧、什么时间"（结果区时间戳 + 明细序号 + 日志同源）。
- 所有新增文案为中文，且不出现"无此功能 / 未实现 / 错误码"这类无行动指引的表述。
- 在 Windows 缩放 100% / 125% / 150% 三档下，右栏不得出现控件重叠、文字截断、分隔条不可拖。**已知风险**：现状结果区是固定 220 px 硬值，改版必须改为相对/可拖值，否则 150% 下 288 px 内容宽会进一步缩水（可能降至约 240 px），两行高的节点行需在此宽度下仍不折行错位。
- 本文 UI-R01/R02 改的是右栏容器与结果区，v3 的 T04 会在参数区新增"框选 ROI / 预览矫正图"等控件：**参数区分组结构须一次预留到位**，避免 T04 落地后再次重排（见 Q16）。
- 本文 OCR-T01/T02 与 v3 的 T03（OCR 字符框/结果标注）在"字符框"上有重叠：本文明确定义 **框的语义归 T03、框的数据与显示开关归本文 R07**，实现时以一侧为准、不得两套并行。

→ 通用约定（坐标系、端子、主题、权限、日志等）见 [知识图谱 §2](../README.md) 与 [增量架构设计 §7](../架构/增量架构设计.md#arch-common)，此处不复述。
