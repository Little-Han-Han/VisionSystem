## P0 — 需要用户补充环境才能完成

### 1. 海康相机只做了框架，未接真实取流

**现状**：`Camera/HikCamera.cs` 实现了完整的 `ICamera` 契约，并附带 `HikSdk` 探测逻辑，但未安装 MVS SDK，因此：
- `HikSdk.TryLoad()` 在常见路径找不到 `MvCameraControl.Net.dll` → 返回 false
- `Open()` / `StartGrab()` 会返回明确错误："未检测到海康 MVS SDK…"
- 真实取流的分支在源码中以 `// TODO(SDK):` 标注

**为什么跳过**：本机没有 MVS SDK，无法确认 `MyCamera` 各 API 的准确签名，盲写反射调用反而容易埋坑。

**补全步骤**：
1. 安装海康 MVS（默认 `C:\Program Files (x86)\MVS`）
2. 在 `VisionPlatform` 项目中添加对
   `MVS\Development\DotNet\MvCameraControl.Net.dll` 的引用
3. 替换 `HikCamera.cs` 中 4 处 `// TODO(SDK):` 分支，参考流程：
   ```
   MV_CC_EnumDevices → MV_CC_CreateHandle → MV_CC_OpenDevice
   → MV_CC_SetEnumValue(TriggerMode) → MV_CC_StartGrabbing
   → 取流线程 MV_CC_GetOneFrameTimeout → MV_CC_StopGrabbing → MV_CC_CloseDevice
   ```

**当前可用的替代**：模拟相机 `SIM-0`，能跑通"取帧 → 算法 → 显示 → 判定"全链路。

## P2 — 工程与环境注意事项

这些问题**已经解决**，但容易再踩，记录在此：

| # | 现象 | 原因与处理 |
|---|---|---|
| 9 | `error : 元素 <WarningLevel> 具有无效值"3"` | VS2022(v143) 的 CL 任务要求写成 `Level3`，不是 `3`。已在 vcxproj 修正。 |
| 10 | `error MSB6001: "CL.exe" 命令行开关无效 … 关键字:"https_proxy"` | 宿主 shell 同时注入了大小写不同的代理变量，MSBuild 用不区分大小写的字典构建子进程环境时冲突。`build-platform.bat` 里已清空这些变量。 |
| 11 | bat 脚本报 `'xxx' 不是内部或外部命令` | **bat 文件必须纯 ASCII**：中文在 cmd 的 GBK(936) 代码页下会乱码，破坏命令解析。`build-platform.bat` 的注释已全部改英文。 |
| 12 | C++ 报 `C4819` + `C2447: "{": 缺少函数标题` | 源文件含中文注释，GBK 下解析错误会**破坏后续函数签名**。已在 vcxproj 加 `/utf-8` 编译选项解决。 |
| 13 | OpenCV 只有 vc14/vc15 的 lib | 用 v143 工具集链接 `vc15/lib` 的 `opencv_world455.lib` —— MSVC 2015~2022 ABI 兼容，已实测通过。 |
| 14 | C# 侧 `Recipe` 被误认为命名空间 | 命名空间 `VisionPlatform.Recipe` 与类 `Recipe` 同名。UI 层用 `using RecipeModel = VisionPlatform.Recipe.Recipe;` 别名规避。 |
| 15 | `OpResult` 无法隐式转 `OpResult<T>` | `OpResult<T>` 只有单参数 `Fail(string)`；带 `params` 的重载在基类且返回 `OpResult`。调用处改用 `string.Format` 即可（或给 `OpResult<T>` 补一个 params 重载）。 |

### USB 相机采集失败修复（2026-10-05 续）

用户反馈「USB 相机采集失败，不能实时显示」。原生层（ctypes 实证）在本机可 `enum=1 / open→640×480 / 5 帧 OK`，故故障位于 ctypes 未覆盖的 C# 集成与显示路径。修复如下：

| 问题 | 根因 | 修复 |
|---|---|---|
| 枚举只探 DShow，漏掉 MSMF-only 摄像头 | `CameraEnum` 仅用 `CAP_DSHOW` 探测，而 `CameraOpen` 自动模式优先 MSMF；Win10/11 上许多 UVC/USB 摄像头 MSMF 才可用 → 不被枚举、列表里没有 → 「采集失败」 | `CameraEnum` 改为「MSMF 优先、回退 DShow」逐个索引探测（与 `CameraOpen` 顺序一致），且首个失败不中断（continue），避免 index 0 失效掩盖 index 1+ |
| 打开后分辨率未知导致静默无显示 | `LocalCamera.Open` 依赖 `cap.get(FRAME_WIDTH)` 即时返回；个别后端打开瞬间返回 0 → `_width/_height=0` → `GrabLoop` 立即报错退出、且错误只记日志不提示用户 | `CameraOpen` 从探测帧直接记录真实分辨率写入 `cam->width/height`；`CameraGetSize` 优先返回该值；分辨率仍未知时 `Open` 显式失败并给出原因（设备未就绪/被占用），不再静默 |
| 采集错误对用户不可见 | `ErrorOccurred` 仅 `Logger.Error` | `CameraForm` 将错误同步到状态栏，且 `GrabLoop` 致命错误附带 C++ `LastError` 文本，便于定位（设备被占用 / 读帧失败等） |
| 首个实时帧未按窗口适配 | 连续预览 `SetImage(bmp, false)` 不 Fit，画面可能只显示局部、观感像「没显示」 | 首个实时帧做一次 `FitToWindow` |

验证：Debug/Release 双配置构建通过；ctypes 端到端实证 `enum=1 / open / get_size=640×480 / 连续 5 帧全 OK / close`；因沙箱无 GUI 与真实多相机环境，跨机差异（MSMF-only、被其他程序占用）需用户在自身机器上确认。

## 本轮（2026-10-26 晚）：OCR「置信度 0」+ 模板目录回程序目录 + 结果显示重做

### 1) OCR 能分割、但全部 `?`、置信度 0.00

**根因（现场样本已核对）**：用户入库的模板是 `N3O.png`（68×145，**三个字符竖排**）。
本引擎是「先分割成单字符框 → 逐框与模板算相关系数 → 取最高分」，
一个三字符模板与任何单字符框都无法相关（得分 ≤0 被钳成 0）→ 全 `?`、meanScore 0.00，且**没有任何提示**。

**修法**
| 位置 | 处理 |
|---|---|
| `OcrCharStore.ValidateLabel` | **一个模板 = 一个字符**（按文本元素计数）。多字符直接拒绝，并在提示里说明"多字符模板永远匹配不上单字符框"。`N3O` 这类再也进不了库 |
| 原生 `algo_ocr.cpp` `MakeBinary` | 极性判据由"前景占比 >50% 才反色"改为**边框环**判据（环上多为亮 → 反色），面积法只作兜底。紧裁模板（字形占多数）不会再被存成"背景负形" |
| 原生 `OcrRecognizeEx` | 未采纳字符也**照实输出原始最佳分**（label 仍是 `?`），上层才能说清"最高只有 0.32" |
| `FlowRunner.RunOcr` | 新增"认出数"统计；有模板但**一个都没认出**时：摘要点名"全部低于接受阈值（最高 x.xx）"并给出排查方向，节点状态 **Warn（不是 OK）** |
| `NodeParamSchema.Ocr` | 说明文案补两条硬约束：一个模板一个字符、字符方向必须与现场一致 |

### 2) 模板保存路径

- 新建 OCR 节点的默认目录回到 **相对路径 `OCRModel`** → 运行时解析为 `<程序目录>\OCRModel`（Release 即 `bin\x64\Release\OCRModel`）。
- `AppPaths.OcrCharsDir` 一并改到程序目录（管理窗体的"迁移到…"默认目标）。
- **旧配置自动迁移**：`FlowSettings.MigrateOcrTemplateDir` 把 `...\OcrChars` 绝对路径改回 `OCRModel`；用户自定义的绝对目录不动。
- 旧的 `%AppData%\VisionPlatform\OcrChars`（N3O.bmp / N3O.png 两个坏样本）已备份到
  `%TEMP%\vs_ocr_backup_20261026_214739\` 后删除。

## 补丁（10-28 晚）：位置修正对卡尺/OCR 的 ROI 不生效 —— 根因是**执行顺序**

用户："OCR、卡尺工具的位置修正并未启用，ROI 并没有修正"。

### 根因（不是没接线）
位置修正是**链级全局状态**（写 `session.Transform`，或把工作帧 warp 回基准姿态），
下游只要"在它之后执行"就会自动生效。但执行顺序只由 **连线 + (X, Y, Id)** 决定：

- 卡尺/OCR 的 `Image` 通常直接连**图像源**（不连位置修正节点）；
- 于是在画布上位置修正节点只要排得靠右，卡尺/OCR 就会**先执行** ——
  此时 `Transform` 还是空的、图也没对齐 → ROI 用的是原始坐标 → 现场就是"没修正"。

### 修法：位置修正"全局先行"
`FlowOrder.ApplyPositionCorrectFirst()`：在 Kahn 排序前，给**要用 ROI 的节点**
（Blob / 直线卡尺 / 圆卡尺 / OCR / 清晰度 / 颜色提取 / 滤波 / 拟合 / 目标识别）
补一条虚拟依赖「位置修正 → 该节点」。三条约束：
1. 只对**已有连线**的图内节点生效（孤立节点保持孤立，W001 警告照旧）；
2. 已有直接连线的不重复加；
3. **成环保护**：若从该节点沿下游能走到位置修正（用户的数据流本来就是 卡尺→位置修正），跳过。
   注意方向：要查的是"cid 顺流能否到 pid"，写成"找祖先"会漏判并自己造环（本轮踩过）。

### 让用户"看得见"
`FlowRunTransform` 新增 `Warped` 标记 + `PoseNote()`：
- 修正烘进像素后（warp 路径）→ 卡尺/OCR 摘要追加「　· 图像已按位置修正对齐」
- 只做坐标映射时 → 追加「　· ROI 已按位置修正映射(dX=…,dY=…,dA=…)」
- 没有这句 = 本帧确实没修正（该去查链上有没有位置修正节点、是否被跳过）

### 验证（对照实验，SmokeAlgo T11b）
同一张**整体漂移 (+40,+30)** 的合成图：
| 链 | 结果 |
|---|---|
| 图像源 → 匹配 → **位置修正** → 直线卡尺 | 卡尺 OK：长度 200.0，有效点 10/10，摘要带「图像已按位置修正对齐」 |
| 图像源 → 匹配 → 直线卡尺（无位置修正） | 卡尺 **NG：有效边缘点 0 < 3**（ROI 扫在空处） |

另加 `TestPoseFirstOrdering`：把位置修正摆到画布最右侧、卡尺/OCR 只连图像源，
断言排序为 `src → sm → pc → cal → ocr`；再构造"卡尺→位置修正"的真实数据流，断言不成环。

## 补丁（10-28 21:5x）：位置修正"完全没反应"的**真正**根因 —— Auto 基准每次运行都被重新示教

前面两轮修了「执行顺序」和「ROI 偏移」，但用户仍然看不到效果。真正的原因是基准的**生命周期**：

```
Begin(clearAutoRefs: true) → 清空 _autoRefs → 本帧视为"首帧" → 示教（基准=当前位姿）→ dX=0
```
即"**点一次跑一次**"的用法里，**每次运行都会把基准重新设成当前位姿**，dX/dY 恒为 0。
连续运行（Loop)才在循环外清一次，所以只有连续模式才看得出偏差 —— 这正是"没有任何反应"。

### 修法：基准必须示教一次、落盘、之后一直比（同 VisionMaster/HALCON）
- 新增隐藏参数 `AutoRefX / AutoRefY / AutoRefA / AutoRefSet`（`RefSource=Auto` 时用）。
- 首次运行：把上游位姿写进这四个参数，`FlowRunResult.BaselineTaught = true`；
  宿主（FlowForm）看到后立刻 `SaveFlows()` 落盘 + 状态提示。
- 之后每次运行：直接读节点里已示教的基准 → 与实时位姿比较 → 得到真实的 dX/dY/dA。
- 重新示教：把「基准已示教」置 0（参数隐藏，需要时手改配置）。

### 仿射是怎么算的（回答"如何仿射 ROI"）
`FlowRunTransform.ApplyToPoint`：
```
p' = R(dA)·(p − Ref) + Ref + (dX, dY)     // 绕基准点旋转，再平移
```
- **卡尺**：扫描线两端点各走一次 `ApplyToPoint`；扫描角 `ApplyToAngle(θ) = θ + dA`
  —— 点级仿射，旋转是<strong>真的</strong>（不是外接框）。
- **BLOB / OCR**：`ApplyToRect` 返回旋转后的**外接矩形**（AABB）。
  平移工况完全正确；dA≠0 时 ROI 会"变胖一点"（外接框），识别仍能跑，但框不是贴合旋转的。

### 验证（两次独立运行，模拟"点一次跑一次"）

|---|---|---|
| 第 1 次（参考图） | 示教基准，dX=dY=0，BaselineTaught=true | ✓ |
| 第 2 次（漂移图 +40/+30） | dX=40.00、dY=30.00 | ✓ 偏差 0.00 px |
| 第 2 次卡尺投影窗中心 y | 130 | ✓ 130.00 |
| 仿射数学（dA=90°，基准 320,240） | (420,240) → (360,370)；扫描角 0°→90° | ✓ 全部 0 偏差 |

用户："提高形状匹配的精度/鲁棒性，重点解决大角度搜索太慢。"

### 先量后改（基线，改动前）

| 场景 | Debug | Release |
|---|---|---|
| A 同姿态（1 姿态） | 37.8 ms | 4.8 ms |
| B 旋转 17°（37 姿态） | 68.0 ms | 11.4 ms |
| C 旋转+缩放 | 200.0 ms | 40.5 ms |
| **D 全角度 360 姿态 @1280×960** | **790.0 ms** | **162.1 ms** |

内层是"逐姿态 × 逐点算 `atan2` 再取余弦"，360 姿态就是 360 遍三角函数 —— 这是大角度慢的根因。

### 改法（保留金字塔 / 候选 / NMS / 亚像素，对外 API 不变）

| 手段 | 说明 |
|---|---|
| ① 梯度方向量化 | `kDirBins = 32` 档（最坏 5.6° 量化误差，cos 误差 ≤0.005）。图像每个像素的梯度方向一次性 `cv::phase` 向量化算好存 1 字节；模板各层也存一份 |
| ② 旋转 = 档位平移 | 纯旋转下"模板点方向"与"图像点方向"的夹角等于 `(图像档 − 模板档)` 绕圈相减，所以某个姿态的模板档位 = 基准档位整体 `+round(angle·32/360)`。姿态预计算阶段一次做完，**内层不再有任何三角函数** |
| ③ cos 响应表 `g_dirCos` | 32×32 = 1024 float = 4KB，常驻 L1。内层变成"读 1 字节 + 查表 + 累加" |
| ④ 边缘支持度积分图剪枝 | 同趟生成"有梯度"mask 再过 `cv::integral`。搜索位置按模板外接圆矩形查积分图，`cnt == 0` 直接跳过该位置 —— 这是**严格上界**（模板落在这里一分也拿不到），不是启发式 |
| ⑤ 只在粗层启用 | `useFast = (L0 >= 1) && (coarseWork >= kFastPathMinWork) && !ForcePrecise()`：粗层本来就降采样（1px 误差可接受），最细层仍走精确双线性 + 精确 `atan2`，保亚像素 |

|---|---|---|---|---|
| A 同姿态 | 38.2 ms | — | 4.2 ms | — |
| B 旋转 17° | 42.0 ms | **−38%** | 6.1 ms | **−46%** |
| C 旋转+缩放 | 66.7 ms | **−67%** | 13.4 ms | **−67%** |
| **D 全角度 360 姿态** | **154.1 ms** | **−80%（5.1×）** | **23.9 ms** | **−85%（6.8×）** |

A 略慢 0.4ms（噪声级）：`coarseWork < 400000` 时门槛把查表关掉，走原精确路径 —— 否则建方向图 + 积分图的一次性开销在小搜索上摊不回来（实测会把 A 从 38.5 拖到 41.8）。

### 精度没有退化

原 6 条断言全绿且数值与改动前一致：B 角度误差 0.00°、C 缩放误差 0.000、D 角度误差 0.00°，得分仍为 0.981 / 0.985。
另补两条鲁棒性用例：**BENCH-I**（前景 190 灰 + sigma=8 噪声，seed 固定）得分 0.992、位置误差 0.707px；**BENCH-J**（同前 + 旋转 17°）得分 0.978、角度误差 0.25°。

### 断言收紧（不是放宽）

`BENCH-D 耗时` 门限 **1500ms → 600ms**。理由：1500 是最初的目标值，而优化后 Debug 154ms / Release 24ms；
若把 `useFast` 判据或 `kFastPathMinWork` 改坏，耗时会掉回 800ms 级 —— 1500 的门限**照样 PASS**，回归静默溜走。
600ms 对新实现仍留 ~4× 余量（Debug），但能抓住"查表路径整体没生效"。A/B/C 三条仍保留原始目标值。

### 踩过的坑（已修，记录以防再犯）

| 现象 | 根因 |
|---|---|
| 改完 **全部 0 命中**，最佳候选落在图像边缘且得分 ~0.4 | `cv::phase(gx, gy, ang, false)` 返回**弧度**（第 4 参 `angleInDegrees` 要传 `true`），代码按"度→档位"换算 → 所有像素落到档位 0 |

### 4) 关于「流程内节点并行」——结论：暂不做，先给方案
现状是**严格串行**（拓扑序，一次一个节点）。要并行有三个硬约束：
1. `session.Current` 是**单一共享工作帧**（任何节点都可能替换它）；
2. 原生算法 `_algo` 是**单实例**（并发调用同一 Context 未做线程安全）；
3. 结果通道/相机锁（`CameraGrabLock`）都是单通道模型。
可行的做法是"每个并行分支一条独立 session（帧拷贝 + 独立算法上下文），最后合并进度与结论"，
代价是内存翻倍、调试复杂；而**单帧检测当前多在 10ms 级**（形状匹配 360 姿态已从 818ms 降到 154/24ms），
并行收益远小于复杂度。**建议**：先不做并行；若确有多路需求（多相机 / 大图多算法），
按"分支 session + 结果合并"单独立项。
