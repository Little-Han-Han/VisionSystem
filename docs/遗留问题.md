## P0 — 需要用户补充环境才能完成

### 1. 海康相机只做了框架，未接真实取流

**现状**：`Camera/HikCamera.cs` 实现了完整的 `ICamera` 契约，并附带 `HikSdk` 探测逻辑，但未安装 MVS SDK，因此：
- `HikSdk.TryLoad()` 在常见路径找不到 `MvCameraControl.Net.dll` → 返回 false
- `Open()` / `StartGrab()` 会返回明确错误："未检测到海康 MVS SDK…"
- 真实取流的分支在源码中以 `// TODO(SDK):` 标注

**为什么跳过**：本机没有 MVS SDK，无法确认 `MyCamera` 各 API 的准确签名，盲写反射调用反而容易埋坑。

**补全步骤**：
1. 安装海康 MVS（默认 `C:\Program Files (x86)\MVS`）
2. 在 `VisionPlatform` 项目中添加对
   `MVS\Development\DotNet\MvCameraControl.Net.dll` 的引用
3. 替换 `HikCamera.cs` 中 4 处 `// TODO(SDK):` 分支，参考流程：
   ```
   MV_CC_EnumDevices → MV_CC_CreateHandle → MV_CC_OpenDevice
   → MV_CC_SetEnumValue(TriggerMode) → MV_CC_StartGrabbing
   → 取流线程 MV_CC_GetOneFrameTimeout → MV_CC_StopGrabbing → MV_CC_CloseDevice
   ```

**当前可用的替代**：模拟相机 `SIM-0`，能跑通"取帧 → 算法 → 显示 → 判定"全链路。

## P2 — 工程与环境注意事项

这些问题**已经解决**，但容易再踩，记录在此：

| # | 现象 | 原因与处理 |
|---|---|---|
| 9 | `error : 元素 <WarningLevel> 具有无效值"3"` | VS2022(v143) 的 CL 任务要求写成 `Level3`，不是 `3`。已在 vcxproj 修正。 |
| 10 | `error MSB6001: "CL.exe" 命令行开关无效 … 关键字:"https_proxy"` | 宿主 shell 同时注入了大小写不同的代理变量，MSBuild 用不区分大小写的字典构建子进程环境时冲突。`build-platform.bat` 里已清空这些变量。 |
| 11 | bat 脚本报 `'xxx' 不是内部或外部命令` | **bat 文件必须纯 ASCII**：中文在 cmd 的 GBK(936) 代码页下会乱码，破坏命令解析。`build-platform.bat` 的注释已全部改英文。 |
| 12 | C++ 报 `C4819` + `C2447: "{": 缺少函数标题` | 源文件含中文注释，GBK 下解析错误会**破坏后续函数签名**。已在 vcxproj 加 `/utf-8` 编译选项解决。 |
| 13 | OpenCV 只有 vc14/vc15 的 lib | 用 v143 工具集链接 `vc15/lib` 的 `opencv_world455.lib` —— MSVC 2015~2022 ABI 兼容，已实测通过。 |
| 14 | C# 侧 `Recipe` 被误认为命名空间 | 命名空间 `VisionPlatform.Recipe` 与类 `Recipe` 同名。UI 层用 `using RecipeModel = VisionPlatform.Recipe.Recipe;` 别名规避。 |
| 15 | `OpResult` 无法隐式转 `OpResult<T>` | `OpResult<T>` 只有单参数 `Fail(string)`；带 `params` 的重载在基类且返回 `OpResult`。调用处改用 `string.Format` 即可（或给 `OpResult<T>` 补一个 params 重载）。 |

### USB 相机采集失败修复（2026-10-05 续）

用户反馈「USB 相机采集失败，不能实时显示」。原生层（ctypes 实证）在本机可 `enum=1 / open→640×480 / 5 帧 OK`，故故障位于 ctypes 未覆盖的 C# 集成与显示路径。修复如下：

| 问题 | 根因 | 修复 |
|---|---|---|
| 枚举只探 DShow，漏掉 MSMF-only 摄像头 | `CameraEnum` 仅用 `CAP_DSHOW` 探测，而 `CameraOpen` 自动模式优先 MSMF；Win10/11 上许多 UVC/USB 摄像头 MSMF 才可用 → 不被枚举、列表里没有 → 「采集失败」 | `CameraEnum` 改为「MSMF 优先、回退 DShow」逐个索引探测（与 `CameraOpen` 顺序一致），且首个失败不中断（continue），避免 index 0 失效掩盖 index 1+ |
| 打开后分辨率未知导致静默无显示 | `LocalCamera.Open` 依赖 `cap.get(FRAME_WIDTH)` 即时返回；个别后端打开瞬间返回 0 → `_width/_height=0` → `GrabLoop` 立即报错退出、且错误只记日志不提示用户 | `CameraOpen` 从探测帧直接记录真实分辨率写入 `cam->width/height`；`CameraGetSize` 优先返回该值；分辨率仍未知时 `Open` 显式失败并给出原因（设备未就绪/被占用），不再静默 |
| 采集错误对用户不可见 | `ErrorOccurred` 仅 `Logger.Error` | `CameraForm` 将错误同步到状态栏，且 `GrabLoop` 致命错误附带 C++ `LastError` 文本，便于定位（设备被占用 / 读帧失败等） |
| 首个实时帧未按窗口适配 | 连续预览 `SetImage(bmp, false)` 不 Fit，画面可能只显示局部、观感像「没显示」 | 首个实时帧做一次 `FitToWindow` |

验证：Debug/Release 双配置构建通过；ctypes 端到端实证 `enum=1 / open / get_size=640×480 / 连续 5 帧全 OK / close`；因沙箱无 GUI 与真实多相机环境，跨机差异（MSMF-only、被其他程序占用）需用户在自身机器上确认。

用户反馈「界面太丑、导航栏上的内容不明显、按钮 / Tab / 表格等控件可以重做」。本轮做了控件级重建与全窗体主题接入。

| 新增文件 | 作用 |
|---|---|
| `UI/UiButton.cs` | 自绘圆角按钮：默认 / 悬停 / 按下 / 禁用 / 聚焦五态，`Kind` 决定语义色（Start 绿 / Pause 橙 / Stop 红 / Grab 蓝 / Reset 灰 / Neutral 卡片底） |
| `UI/UiToolStripRenderer.cs` | 导航栏渲染器：条目画成「胶囊 chip」而非扁平文字；支持 `SetChipKind()` 给启动 / 暂停 / 采集上语义色；可见分隔线、底部分层线、加粗 10.5pt |
| `UI/UiTabControl.cs` | 自绘选项卡：选中态强调色 + 白字，含 `StylePage / StyleAllPages`（当前工程尚无 TabControl，作为统一控件备用） |
| `UI/UiGrid.cs` | 表格主题化：关系统蓝表头、34px 表头 / 28px 行、隔行换色、强调色选中、填充式布局 |
| `UI/UiStyle.cs` | **整窗体主题递归套用**：一行 `ApplyForm(this)` 把整棵控件树换成深色工程配色 |

关键设计取舍：

- **只覆盖"系统默认色"控件**：`IsSystemColor()` 判定，设计器里刻意写死的深色（标题条、模块列表 `FromArgb(30,30,38)` 等）一律保留，避免抹平已有层次。
- **不改 `Form.Font`**：Designer 多为 `AutoScaleMode.Font`，运行时改字体会触发整窗重新缩放把布局撑变形；子控件字体逐个覆盖即可。
- **自绘控件整棵子树跳过**：`UiButton`、`VisionSystem.Controls.*`（ImageViewer）、`FlowCanvasControl / FlowPreviewPanel / NodeParamPanel / UiTabControl` 自己管配色。
- **语义色只给"一看就要点"的动作**：导航栏里只有启动 / 暂停 / 单帧 / 同步采集上色，其余保持中性卡片底，避免整条花掉。

接入范围：`AlgoForm / CameraForm / SettingsForm / RecipeForm / CommForm / LoginForm / FlowForm` 由 `UiStyle.ApplyForm` 统一接入（此前这 7 个窗体完全游离在主题之外，是系统浅色控件）；`MainForm` 沿用其手写的 `ApplyTheme()`。共 39 个按钮从 `Button` 换成 `UiButton`。

### 并行引擎 `MaxParallelFlows` 缺失值补默认（2026-10-11）

`SmokeParallel` 硬验收发现：旧配置没有 `MaxParallelFlows` 字段 → 反序列化为 0 → `ClampMaxParallelFlows(0)` 抬到下界 **1**，等于把并行功能悄悄关成"一次只跑一条"。

| | 处理 |
|---|---|
| `UiSettings.ClampMaxParallelFlows(int)` | 语义收窄为**用户输入**钳制（0→1、99→8），保持不变 |
| `UiSettings.NormalizeMaxParallelFlows(int)` | 新增：0 / 负数视为字段缺失 → 补默认值 **4**，其余再 Clamp |
| `ConfigStore.Load()` / `UiSettings.Clone()` / `FlowRunManager.MaxParallelFlows` | 三处改用 `NormalizeMaxParallelFlows` |
