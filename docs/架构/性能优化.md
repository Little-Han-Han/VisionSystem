# 流程运行性能：软件层开销分析与优化

> 目标：回答"还能优化什么、为什么比 Halcon / Cognex 慢"。
> 本文只讨论**软件层**（调度、日志、拷贝、UI 回传）；算法本身（OpenCV/C++）单列在 §7。
>
> 实测环境：本机 Debug/Release，`SmokeAlgo` 内置基准（`BENCH_FLOW=1`）。
> 关联代码：`Core/Logger.cs`、`Flow/FlowRunController.cs`、`Flow/FlowRunSlot.cs`、
> `Flow/FlowRunner.cs`、`Flow/FlowRunContext.cs`、`Core/AppSettings.cs`。

---

## 1. 结论（先看这里）

| 优化项 | 优化前 | 优化后 | 说明 |
|---|---|---|---|
| 每帧一条 RESULT 日志 | **6.5 ~ 7.1 ms** | **0.009 ~ 0.010 ms** | 同步 `File.AppendAllText` → 后台批量写；约 **700×** |
| 循环运行硬限帧 | 固定 33 ms（≈30 fps） | 默认不限制，可配置 | 算法再快也被压到 30fps，是最容易被误判为"软件慢"的一项 |
| 并行生产运行的整幅帧副本 | 每帧 2 份（原图 + 节点帧） | 0 份 | `FlowRunSlot` 不看这两类帧，按需关闭 |
| 拓扑序重建 | 13.7 µs/帧 | 未改（不值得） | 12 节点实测，占 33ms 的 0.04% |
| 参数读取 `GetDouble` | 233 ns/次 | 未改（占比较小） | 200 次/帧 ≈ 47 µs |

**一句话**：软件层最贵的三件事是 —— ①每帧同步写日志；②算法并行度失控（OpenMP 开满核，
4 条流程 48 个线程抢 12 核）；③界面每帧重刷（白建图像金字塔）。三项都已处理，
实测 4 条流程 **96% CPU / 48 fps → 34.9% CPU / 107 fps**。

剩下的差距才来自算法实现本身（模板匹配策略、金字塔层数、SIMD/指令集、内存布局）。

---

### 连续运行 CPU 高的排查顺序（照这个顺序，别乱改）

1. `VA_PERF_STATS=1` 跑 30 秒，看 `[性能]` 行：**界面占几核？算法占几核？线程有几个？**
2. 界面 > 1 核 → 看 4.4（金字塔 / 浮点矩形 / 状态栏节流）；
3. 线程数远大于"流程数 + 常数"、且与帧率无关 → 看 4.5（OpenMP 开满核）；
4. 都正常但 CPU 仍高 → 那是算法本身的量，只能降节拍（`Ui.MaxFlowFps`）或优化算法。

## 3. 每帧时间都花在哪（软件层视角）

```text
相机 GrabOne / 读文件
   └─ 图像源节点：ROI / 旋转 / 镜像（可能整幅写）
        └─ 各算法节点（C++/OpenCV，占大头） ← 看 FlowNodeProgress.ElapsedMs
             └─ Finish：拼接摘要、收集图形
                  └─ 发布：预览帧 / 主界面帧 / 原始帧
                       └─ 日志：RESULT 一行
                            └─ 限帧等待（旧 33ms）
```

逐项：

| 环节 | 旧成本 | 备注 |
|---|---|---|
| 算法节点 | 几 ms ~ 几十 ms | 真正的瓶颈，见 §7 |
| RESULT 日志 | **6.5 ms/帧** | 同步开关文件；多流程还在同一把锁上排队 |
| 限帧等待 | 最长 33 ms/帧 | 算法 5ms 也要等到 33ms 才下一帧 |
| 原图副本 | 1 次整幅克隆 | 只有预览面板要看"原图" |
| 节点帧副本 | 每节点 1 次克隆 | 只有单步 / 点开节点看画面才需要 |
| 预览帧 | 1 次克隆 | 预览面板需要 |
| 拓扑重建 | 13.7 µs | 可忽略 |

## 4. 已实施的优化

### 4.1 日志改后台批量写（最大单项）

`Core/Logger.cs`：

- `Info/Warn/Result` 只做 `LogEntry.Format()` + 入队，后台线程每 200ms 批量追加；
- `Error` 仍**同步落盘**（先刷队列再追加），保证崩溃现场可查；
- `Logged` / `EntryLogged` 事件保持同步触发，UI 与 `LogDb` 行为不变；
- 退出时 `Logger.Shutdown()` 做最后一次刷盘（`Program.Main` 已接入）。

效果：6.5ms → 0.010ms/条；多流程不再互相等文件锁。

### 4.2 解除 30fps 硬限，改为可配置

新增 `UiSettings.MaxFlowFps`：

| 值 | 含义 |
|---|---|
| `0`（默认） | 不限制，按相机/算法实际能力跑 |
| `30` / `60` | 主动限帧，降低 CPU 与日志量 |
| 上限 | 1000 |

`FlowRunController`（FlowForm 连续运行）与 `FlowRunSlot`（MainForm 全部启动）
统一走 `Flow/FlowRateLimit.cs`，不再各自写死 33ms。

> 实测（SmokeUi 并行引擎用例）：同一套两条流程，旧版被压在 30fps；
> 新版 A=62.9 fps、B=254.8 fps（本地图片流不受相机帧率限制）。

### 4.3 按运行模式关闭无用的整幅帧副本

`FlowRunSession` 新增两个开关：

- `CaptureSourceFrame`：仅 `FlowRunController.LoopCore`（预览要显示原图）打开；
- `CaptureProgressFrames`：`FlowRunSlot`（并行生产）关闭，不再为每个节点克隆画面。

图像源里的 `SourceFrame = work.Clone()` 与 `EnsureNodeFrame()` 都会先检查开关。
并行生产每帧因此少 2 次整幅克隆（以及后续写时复制的页拷贝）。

### 4.4 连续运行时界面不再"每帧全量重刷"（界面侧）

> 先说结论：界面侧确实有浪费（每帧白建 620~833ms 的金字塔），已在本节修掉；
> 但如果 CPU 依然打满，真正的大头在 **4.5 的算法并行度**，先看那一节。

> **症状**：一按「全部启动」CPU 立刻上到满格，但把流程停了 CPU 就掉下来；
> 算法单节点耗时看起来并不高。这时基本可以断定是**界面在跟着每一帧重刷**。

逐个查过之后，真正每帧都在做无用功的是下面这几处（全部已改）：

| 位置 | 原来（每帧） | 现在 | 实测（本机 Debug） |
|---|---|---|---|
| 视图缩放 | 重建 **12 层**金字塔，且用 `HighQualityBilinear` | 连续流**不建金字塔**，直接按屏幕尺寸双线性采样；静止才建，且只建会被选中的层 | 5MP 换图+重绘 **60.7 → 16.1 ms** |
| 缩放目标矩形 | `zoom` 算出的**浮点**矩形 | `zoom<1` 时取整走 GDI+ 快路径 | 同图同尺寸：整数 14.7ms / 带小数 **35.0ms** |
| 帧所有权 | 每帧先 `Clone()` 一份 5MP（15MB） | 直接移交视图（`SetImage` 接管所有权） | 省 15MB/帧的纯拷贝 |
| 状态栏 + 统计卡片 | 每帧两行 `string.Format` + 5 个按钮态 + 4 个标签 | 合并到 **5Hz（200ms）**，计数仍按件精确累加 | 30fps → 5 次/秒 |
| 主徽标 / 视图角标 | 每帧重配一次配色字体 | 结论变化才配 | 同结论连跑几千帧时省掉 |
| 视图标题条 | 每帧拼字符串（`ActiveFlowName` 还 new lambda 扫流程列表） | 文案变了才赋值；流程名解析结果缓存 | — |

**为什么"12 层金字塔"是负优化**：它的本意是让缩放只换层、不重新采样整图。
但连续运行时每帧都是新图，等于每帧都要重采样一遍整图去建层：

```
5MP → 1224×1024：HighQuality 双线性 39.2 ms ｜ 普通双线性 17.6 ms ｜ 最近邻 7.7 ms
5MP → 800×600  ：HighQuality 双线性 30.9 ms ｜ 普通双线性 13.8 ms
```

建层本身比它省下的采样量贵得多。所以现在按「两次换图间隔 < 300ms」判定为连续流，
连续流跳过金字塔并降级插值；流程停下 300ms 后自动回到高质量路径（金字塔 + 精细插值），
**静止画面不会一直是低画质**。

**额外的显示节流**（`MainForm.MinRenderIntervalMs`，默认 66ms ≈ 15fps）：
算法跑多快都行，画面按 15fps 合并。人眼对 15fps 的实时画面几乎无感，
但单视图的缩放开销直接降到 1/2~1/4。需要更高刷新率时：

```bat
set VA_UI_RENDER_FPS=30
```

### 4.5 算法并行度：OpenMP 默认开满核（连续运行 CPU 高的真正大头）

> **一句话**：形状匹配用 `#pragma omp parallel for`，OpenMP 默认按物理核数开满线程；
> 宿主本来就是"每条流程一个线程"并行，于是 N 条流程 = N×核数 个线程抢核数 个核。
> 4 条流程时实测 **48 个线程抢 12 核**，CPU 96%，而吞吐只有 48 fps。

**怎么发现的**（这份排查路径本身就是方法论）：

1. 先做界面优化（见 4.4），CPU 没怎么动 → 说明界面不是主因；
2. 加运行时归因探针（`VA_PERF_STATS=1`）：进程 CPU 96% 但三个流程线程各只 5%，
   剩下 8~11 个"无名线程"各烧满一个核；
3. 把帧率从 57 fps 压到 16 fps，**CPU 一点没降** → 这部分开销与"产出多少帧"无关；
4. `cv::setNumThreads(1)` 也没用 → 不是 OpenCV 的 `parallel_for`；
5. 在源码里 grep `parallel_for_` → 命中 `algo_shape.cpp` 里的 **`#pragma omp parallel for`**（4 处）。

**修法**（三层一起才生效）：

| 层 | 改动 |
|---|---|
| 原生导出 | 新增 `va_set_threads(int)`：同时设 `cv::setNumThreads`、`omp_set_num_threads`/`omp_set_dynamic(0)`，并把预算存进 `va::g_vaThreads` 供 OpenVINO 用 |
| OpenVINO | `ApplyThreadBudget(core)`：建 `ov::Core` 后设 `inference_num_threads` + `num_streams(1)`（推理线程池不受 setNumThreads 影响） |
| 宿主 | `FlowRunManager.ApplyAlgoThreadBudget` 按"整机预算 ÷ 流程数"分配；**每条流程线程启动时再调一次**（`omp_set_num_threads` 是线程局部状态，主线程设一次没用） |

**实测（Release，4 条流程，本机 12 核）**：

| 配置 | CPU | 吞吐 | 线程数 |
|---|---|---|---|
| 旧：OpenMP 开满（12 线程/流程） | 96%（11.5 核） | 48~57 fps | 13+ |
| 新：整机预算 6 核 ÷ 4 流程 = 1 线程/流程 | **34.9%（4.19 核）** | **107 fps** | 5 |

单条流程孤立测（算法本身约 1 核的量）：

| 线程数 | CPU | 帧率 | 每帧 CPU 成本 |
|---|---|---|---|
| 12 | 11.5 核 | 8.3 fps | 1.39 核·s |
| 2 | 2.14 核 | 3.4 fps | 0.63 核·s |

→ 12 线程比 2 线程多烧 5 倍 CPU，只换来 2.4 倍帧率。**小图（1280×960）上并行收益很快见顶**，
多开的线程基本都在同步上空烧。

**怎么调**（`<程序目录>\appconfig.json`）：

```json
{
  "Algorithm": {
    "MaxThreads": 0
  }
}
```

- `0` = 自动：`总预算 = min(8, 核数/2)`，再按在跑流程数平分，至少 1；
- `1`~`N` = 每条流程固定用几个线程（要极限单帧速度就调大，要低占用就调小）；
- 现场临时对比不用改配置：`set VA_ALGO_THREADS=2`。

### 4.6 明确不改的项（避免过度设计）

| 项 | 实测 | 结论 |
|---|---|---|
| 缓存拓扑序 | 13.7 µs/帧 | 收益 < 0.05%，不值得增加失效逻辑 |
| 参数索引/数值缓存 | 233 ns/次 | 200 次/帧 ≈ 47 µs，等算法优化后再看 |
| 会话对象池 | 分配量中等 | 需要重写帧所有权，风险高于收益 |

## 5. 配置方法

`<程序目录>\appconfig.json`（如 `bin\x64\Release\appconfig.json`）：

```json
{
  "Ui": {
    "MaxFlowFps": 0
  }
}
```

- 现场想降 CPU / 降日志量：改成 `30` 或 `60`；
- 想压测极限：保持 `0`，用主界面的 FPS 与单节点耗时判断瓶颈；
- 该值在每次「启动/全部启动」时读取，改完重启流程即可生效。

### 5.1 现场自查：到底是"谁在刷"

连续运行时想确认 CPU 花在界面还是算法上，打开界面统计探针（默认关闭，不产生日志）：

```bat
set VA_UI_STATS=1
VisionPlatform.exe
```

运行期间每 5 秒在日志里输出一条：

```
[UI统计] 5.0s 内：帧显示 74 次（14.8/s）｜状态栏刷新 25 次（5.0/s）｜统计卡片 25 次｜日志行 500 行
```

怎么读：

| 现象 | 说明 |
|---|---|
| 帧显示 ≈ 15/s、状态栏 ≈ 5/s | 正常（显示节流生效） |
| 帧显示 ≈ 30/s 或更高 | `VA_UI_RENDER_FPS` 被设高了，或有多视图在各自刷 |
| 状态栏刷新 ≈ 帧显示次数 | 状态刷新节流失效（回退到每帧刷新） |
| 日志行一直顶到上限 | 日志过滤开了「全部」，连续运行时建议用默认的「结果」 |

单帧真正的缩放代价看 `ImageViewer.LastLayerRebuildMs`（控件公开属性，重建缓存层时更新）；
5MP 图在 fit 视图下应稳定在 15ms 上下，明显高于 25ms 就说明走了慢路径。

## 6. 还能继续优化什么（按性价比排序）

### P0 — 先确认瓶颈在算法还是软件

1. 看 `FlowNodeProgress.ElapsedMs`：哪个节点占 80% 时间；
2. 用 `SmokeAlgo` 的 `BenchShape` / `BenchOcr` 对比同参数纯算法耗时；
3. 若单节点算法已占 90%，软件层优化空间只剩几个百分点。

### P1 — 算法层（收益最大，但属于 C++ 侧）

| 方向 | 说明 |
|---|---|
| 搜索 ROI / 金字塔层数 | 形状匹配把 `SearchW/H` 收到真实区域、`PyramidLevels` 降一层，常是 2~5× |
| 角度/缩放步长 | `AngleStep` 1°→2°、`ScaleStep` 加大，先粗后精 |
| SIMD / OpenMP | 形状匹配方向图、NCC 内积可向量化；OpenCV 已带 TBB/OpenMP，确保没被关掉 |
| 内存布局 | 灰度图统一 `CV_8U` 单通道，避免每节点 BGR↔Gray 转换 |
| OpenVINO | 深度学习节点确认用 CPU 插件多线程（`Device=CPU`），模型转 FP16/IR |

### P2 — 相机与采集

- 海康 `HikCamera` 目前是占位：接 SDK 后应使用**回调取流 + 零拷贝**，不要在 UI 线程 `GrabOne`；
- 本机摄像头 `VideoCapture.read` 阻塞且无超时，高帧率场景建议独立采集线程 + 环形缓冲；
- 多相机场景优先"一相机一流程"，避免共享取帧门串行化。

### P3 — 软件层剩余项

| 项 | 预期 | 风险 |
|---|---|---|
| 预览帧按需克隆（面板隐藏时跳过） | 1 次整幅拷贝/帧 | 低，需要 UI 传可见性 |
| 会话/进度对象池化 | 降 GC（Gen0） | 中，帧所有权复杂 |
| 参数数值缓存 | ~40 µs/帧 | 低 |
| 位图零拷贝传给 C++（`Mat` 包装而非复制） | 取决于现有实现 | 中，需核对每个节点的所有权 |

## 7. 为什么仍可能不如 Halcon / Cognex

软件层优化解决的是"调度与搬运"，不解决"算法常数"：

1. **算法实现差异**：Halcon 的形状匹配/卡尺底层是高度优化的 SIMD + 多尺度搜索，
   同等参数下常数项可能差 3~10 倍；
2. **内存与缓存局部性**：Cognex 的视觉库大量使用预分配缓冲与 SoA 布局，避免每帧分配；
3. **相机链路**：工业相机 SDK 的回调 + 零拷贝，比 `VideoCapture.read` + 每帧 `new Bitmap` 快；
4. **功能边界**：本项目的形状匹配是"教学/工程可用"实现，不是商业库级优化。

**现实目标**：先把软件开销从每帧 ~7ms 降到 <0.1ms，再针对占用最大的算法节点做 ROI/金字塔/SIMD，
通常能把整链从"几十 ms"压到"十 ms 级"；要与 Halcon 持平，需要长期算法投入。

## 9. 维护约定

1. **不要在热路径同步写文件**：日志、图像保存、配置保存都必须异步/批量；
2. **不要重新写死限帧**：统一走 `FlowRateLimit` + `UiSettings.MaxFlowFps`；
3. 新增"每帧一次"的整幅拷贝前，先问"这个消费者真的需要吗"；
4. 任何性能改动都要用 `BENCH_FLOW=1` 或 `ElapsedMs` 给出前后数字，不凭感觉；
5. 软件层优化不得改变判定语义（`Passed` / `Warn` / `Ng` 的红线见架构 §7）。
