# 流程拓扑与并发：现状、边界与扩展路线

> 回答一个常见疑问：**"流程是不是只能单链？不支持分支？"**
> 结论先说：**单条流程已支持有向无环图（扇出 / 汇合），但按拓扑序串行执行**；
> 真正未实现的是「按判定条件择路」和「同一流程内多分支并行」。
>
> 关联代码：`Flow/FlowOrder.cs`、`Flow/FlowRunner.cs`、`Flow/FlowValidator.cs`、
> `Flow/FlowRunManager.cs`；验证：`SmokeUi` 的 T05 / 菱形拓扑用例。

---

## 1. 现状（代码事实）

| 能力 | 是否支持 | 实现位置 / 说明 |
|---|---|---|
| 单链（A→B→C） | ✅ | `FlowOrder.Build` 的 Kahn 拓扑排序 |
| 一个输出接多个下游（扇出） | ✅ | 输出端子可接多条线；只报 `W002` 提示，不阻断 |
| 多路汇入同一节点（汇聚） | ✅ | 入度按"去重后的上游节点数"计算，汇合节点等全部上游完成 |
| 孤立节点（未连线） | ✅ | `W001` 警告，排在拓扑序末尾照常执行 |
| 成环 | ❌ | `E005`，运行前阻断（`FlowOrder` 带环上节点名） |
| 按 OK/NG 条件择路 | ❌ | 当前所有分支都会执行，没有"跳过某条分支"的语义 |
| 同一流程内分支并行 | ❌ | 节点串行执行；并行只在"多流程"维度 |
| 多条流程并行 | ✅ | `FlowRunManager` 每流程独立线程 + 独立 `FlowRunner` + 独立算法上下文 |

### 关键代码

- `FlowRunner.Begin` 不再调用旧的 `TryBuildChain`，而是 `FlowOrder.Build(flow, ...)`；
  注释明确写着"不再要求单链——输出扇出、多路汇聚都能跑"。
- `FlowRunner.StepNext` 按 `session.Chain`（拓扑序）逐个执行；一个节点只执行一次。
- `FlowValidator` 对 Image 端子的扇出只发 `W002`（提示图像分支会复制/共享帧），不是错误。
- `FlowRunManager` 的并行是**流程级**：每条流程一个线程、一个 `FlowRunner`、一个原生 `va::Context`。

---

## 2. 执行语义（必须知道的四条）

1. **一帧一次**：每条流程的一次运行 = 取一帧图像，按拓扑序把整张图跑一遍。
2. **分支都执行**：扇出的每条分支都会跑；没有"判定为 NG 就跳过下游"的机制。
3. **汇合是屏障**：一个节点有多条上游时，必须等所有上游节点执行完才会轮到它（Kahn 入度）。
4. **NG 会传染整条流程**：任一节点返回失败，`session.Passed = false`；
   后续分支仍会继续执行（用于把问题都暴露出来），最终整条流程判 NG。

## 3. 为什么"流程内并行"没有直接做

不是没想过，而是代价与语义问题：

| 障碍 | 说明 |
|---|---|
| 算法上下文是单份的 | `FlowRunContext` 持有当前帧、`RunTransform`（位置修正结果）、颜色通道；并行分支若共享，会互相覆盖 |
| 分支各自的坐标修正 | A 分支做了位置修正、B 分支没做，二者看到的坐标语义不同；并行时必须为每条分支克隆上下文 |
| 图像内存 | 每个并行分支都要独立帧副本（大图时内存翻倍），还要定义分支结束后的帧归谁 |
| 同步点 | 汇合节点要等所有分支；需要定义超时、某分支失败时是否继续等 |
| 相机取帧 | 单相机严格独占（`CameraLease`），流程内并行并不能提高取帧吞吐，收益主要在多相机/多产品场景——那已经由"多流程并行"覆盖 |

因此当前策略是：**流程内用 DAG 表达"都要做"，流程间用多流程表达"同时做"**。
这也是 `FR-PAR-01` 的既定口径。

## 4. 后续扩展路线（按性价比排序）

### 4.1 条件分支（推荐先做，改动中等）

目标：按上游判定选择走哪条路（例如 NG 时走复检分支）。

改造点：
1. `FlowNode` 增加 `BranchCondition`（`Always` / `OnOk` / `OnNg`）与 `BranchSourceNodeId`；
2. `FlowRunner.StepNext` 在节点执行前判断条件，不满足则标记 `Skipped` 并**级联跳过**其独占下游；
3. 汇合节点需要"至少一条分支到达即可执行"的新入度口径（与当前"全部上游"并存，用节点开关选择）；
4. 结果区文案要区分"跳过"与"未执行"，`FlowNodeStatus` 已有 `Skipped` 可复用；
5. 校验器新增：条件分支的判定源必须是上游、且不能形成隐式环。

风险：`Passed` 的聚合语义要重新定义（被跳过分支的 NG 不应算整链 NG）。

### 4.2 流程内并行（改动大，暂不做）

目标：相互独立的分支同时执行，缩短单帧节拍。

改造点：按拓扑层分组 → 每条并行分支克隆 `FlowRunContext`（帧 + 变换）→ 汇合点做 `Barrier`
→ 原生算法上下文按线程隔离（`va::Context` 不是线程安全的）。

风险：内存翻倍、异常聚合、调试难度上升；单相机场景收益有限。
建议等"多相机 + 单流程"的真实需求出现再做。

### 4.3 短期替代方案

- 需要"同时做两件互不影响的事"：拆成两条流程，各自绑定相机/图片源，用「全部启动」并行；
- 需要"都要做但顺序无关"：直接在同一流程里扇出，拓扑序会保证都在汇合节点前完成；
- 需要"NG 才做"：目前只能都做，再在脚本节点里按上游结果决定输出（脚本可读全部上游输出）。

## 5. 验证

| 用例 | 断言 |
|---|---|
| `SmokeUi` T05 扇出 | 图像源 → 预处理 → 结果输出 + 图像源 → 清晰度：4 个节点全部执行，顺序 = 拓扑序 |
| `SmokeUi` 菱形拓扑（本次新增） | 两条分支（Blob）分别来自同一图像源/预处理，汇入结果输出；汇合节点必须排在两分支之后，5 个节点全部执行 |
| `SmokeUi` 成环 | `E005` 阻断，错误文案带环节点 |
| `SmokeUi` 孤立节点 | `W001` 警告，仍排末尾执行 |

## 6. 维护约定

1. **不要重新引入"单链"校验**：执行顺序只由 `FlowOrder` 决定，任何"必须一条链"的判断都会把已支持的扇出打回去。
2. 新增节点若有多输入，明确它是"汇聚（等全部上游）"还是"择一（任一上游即可）"；当前统一按汇聚处理。
3. 流程内并行未实现前，**不要**在节点执行体里起线程共享 `FlowRunContext`；需要并行请走多流程。
4. 条件分支落地时，`FlowNodeStatus.Skipped` 只表示"按条件没走"，**不得**计入 NG（与 `Warn` 的红线一致）。
