## 1. 摄像头接入与流程编排

> 来源 `架构-摄像头与流程编排.md`（2026-10-05）。通用约定见 [§7](#arch-common)。

### 1.1 结论与关键决策

- 本机摄像头接入 · 工程「零第三方依赖」是硬约束，但枚举/取流必须有系统 API · 用**已有的 OpenCV `VideoCapture`（videoio 已在 `opencv_world455.dll` 内）** 在 C++ 层封装，再经既有 P/Invoke 边界暴露给 C#，不引入任何新依赖
- 本机摄像头接入 · 帧率/内存/线程安全 · 采集线程独立 + C# 侧分配缓冲复用（沿用 `CopyOut`「谁分配谁释放」约定）+ `BeginInvoke` 切 UI
- 流程编排 · 画面自由拖拽 / 连线 / 重绘 · **自研 GDI+ 画布控件**（`Control` 子类），不引入任何流程图控件
- 流程编排 · 流程/节点/连线/绑定持久化且向下兼容 · 复用 `AppConfig` 三段式 + `ConfigStore.Load()` 逐段补齐模式
- 流程编排 · 与既有 `InspectionEngine` 循环检测共存 · 流程执行器**独立拥有自己的算法上下文**与相机句柄，不触碰既有循环检测管线
- **决策 1：摄像头走 C++ 层封装 OpenCV `VideoCapture`，C# 仅做 `ICamera` 适配器。**
- 依据（已实测）：`opencv_world455.dll` 已含 `VideoCapture`/`videoio` 符号；导入库 `opencv_world455(d).lib` 齐全；vcxproj 已链好，新增源文件**只需登记，无需改链接配置**。
- ❌ 不用 `System.Windows.Media`（WPF `Capture`)：违反「禁止 WPF」硬约定。
- ❌ 不用 DirectShow 手撸 COM 互操作：工作量大、易错，且 OpenCV 已封装 DShow/MSMF 后端。
- ❌ 不引入 NuGet（如 `OpenCvSharp`、`AForge`）：违反「控件库/主程序零 NuGet」硬约定。
- **决策 2：摄像头用「独立句柄」，不复用算法 `Context` 句柄。**
- 现状导出模式是 `VA_CTX()`（把 `void*` 校验后转 `va::Context*`），错误文本经 `va_get_last_error` 取回。

### 1.3 落地红线与踩坑

- ❌ 不用 `System.Windows.Media`（WPF `Capture`)：违反「禁止 WPF」硬约定。

- **枚举实现说明**：OpenCV 无跨平台枚举 API。采用「探测式枚举」：用 `CAP_DSHOW`（枚举比 MSMF 可靠）对 index 0..N-1 逐个 `open`+`isOpened`，成功计数并立即 `release`。代价是枚举有几百 ms 开销 → 只在「刷新列表」时调用。**局限**：拿不到设备友好名，故 `VA_CameraInfo.name` 留空，由 C# 生成「本机摄像头 n」（符合 PRD Q1）。
- **与 `InspectionEngine` 共存**：`FlowRunner` 走**自己的** `VisionAlgo`（独立 C++ Context）与 `GrabOne`；既有循环检测（`MainForm.OnLoopTick`→`SyncGrabCore`→`RunInspection`→`InspectionEngine`）**完全不动**。二者唯一共享资源是「相机句柄」→ 由 `CameraManager` + 相机自身 `lock` 保证串行取帧。
- 1. **C++ 新增 `.h`/`.cpp` 必须同时登记两处**：`.vcxproj`（`<ClInclude>` / `<ClCompile>`）**与** `.vcxproj.filters`（`<Filter>`）。漏登记会在 VS 里平铺，但不影响编译——**必须都补**。

- 4. **`build.bat` 内容必须是纯 ASCII**；**不在命令行直接跑 MSBuild/devenv**（走 `build.bat`）。
- 6. **修改图形几何属性后必须 `Shapes.NotifyChanged()`** 才会重绘（叠加上流程结果时务必调用）。
- 7. **序列化类型**（进 `appconfig.json` 的）必须标 `[DataContract]` + `[DataMember]`（`Json.cs` 用 `DataContractJsonSerializer`）。枚举**存字符串**、字典**改有序列表**（见 3.3）。
- 11. **结果/错误**：业务返回值用 `OpResult`/`OpResult<T>`；日志用 `Logger.Info/Warn/Error`；不要到处抛异常。

## 2. 界面布局与算法模块

> 来源 `架构-界面布局与算法模块.md`（2026-10-10）。通用约定见 [§7](#arch-common)。

### 2.1 结论与关键决策

- 难点 · 本质 · 本期解法
- ① 12 类节点各有参数，手写面板会爆炸 · 参数 UI 的**规模化**问题，不是算法问题 · 声明式参数面板：`NodeParamSchema`（一张字段表）+ `NodeParamPanel`（一个通用 `UserControl` 动态生成）
- ② 中间结果"逐节点"可见 + 单步/单帧/连续三种运行模式 · 执行内核必须**可分段、可观察**，不能只暴露 `Run()` · 把 `FlowRunner.Run()` 拆为 `Begin()/StepNext()` 会话式内核，三种模式共用；产出的 `FlowNodeProgress` 携带「该节点输出帧 + 该节点图形 + 耗时 + 结论」
- ③ 位置修正要把偏移传给下游 ROI · 执行期需要一条**沿链传递的运行时状态** · 新增 `FlowRunContext`，内含 `RunTransform`（覆盖式，后写胜）；下游节点取 ROI 时统一走 `ApplyToRect()`
- ④ 卡尺是原生层**从零新增**的算法族 · C++ 侧需新建头/源 + 导出 + 工程登记 + P/Invoke 双向结构体对齐 · `va_caliper.h/.cpp` + `VA_CaliperParam/VA_CaliperPoint`，严格沿用「句柄校验 → 转发 → 异常转码 → lastError」既有导出范式
- ⑤ 界面要"醒目"但**禁止图标与第三方库** · 只能靠字号/颜色/留白/区块 · 纯代码静态色板 `UiTheme`；**Designer 只管控件树与布局，`ApplyTheme()` 运行时统一套色**（见决策 2）
- **决策 1：主题用纯代码静态类 `UiTheme`，不用资源文件、不用第三方主题库。**
- PRD `FR-UI-12` 是硬验收项（diff 无二进制资源、无 NuGet 包）。`UiTheme` 是 `static class`，只含 `readonly Color`、`static Font`（懒构造）、`const int` 尺寸常量。
- ❌ 不用 `.resx` 资源字典：会被判为"资源文件"，且无法用常量做布局计算。
- ❌ 不改 `App.Config` / 不引入 JSON 主题文件：本期无换肤需求（PRD 范围外），静态常量最简单、编译期可校验。
- **决策 2：Designer 管结构，`ApplyTheme()` 管外观（颜色/字体）。**
- 现状：`MainForm.Designer.cs` / `FlowForm.Designer.cs` 里散落着 `Color.FromArgb(38,38,46)` 之类的魔法值；若 12 个面板 + 2 个窗体都硬写色值，`FR-UI-01` 的验收②「单点修改全局生效」无法满足。
- 做法：**新增/改动的控件在 Designer 里只写结构（Dock/Size/Text/父子关系），颜色与字体统一在各窗体的 `ApplyTheme()` 里用 `UiTheme` 赋值**（`InitializeComponent()` 之后调用）。
- 好处：色板单点生效；Designer 文件不引入对 `UiTheme` 的硬引用（VS 设计器打开不出错）；评审只需看 `UiTheme` 一处。

### 2.3 落地红线与踩坑

- ⑤ 界面要"醒目"但**禁止图标与第三方库** · 只能靠字号/颜色/留白/区块 · 纯代码静态色板 `UiTheme`；**Designer 只管控件树与布局，`ApplyTheme()` 运行时统一套色**（见决策 2）

## 3. 多相机 · 多产品 · 流程并行

> 来源 `架构-多相机多产品与并行.md`（2026-10-10）。通用约定见 [§7](#arch-common)。

### 3.1 结论与关键决策

- 难点 · 本质 · 本轮解法
- ① N 条流程同时跑，且互不串扰 · 资源隔离 + 生命周期管理 · **流程维度 1:1:1:1 隔离**：1 流程 = 1 `FlowRunner`（→1 原生 `VisionAlgo` 上下文）= 1 线程 = 1 会话；会话每周期重建
- ② 同一相机被多流程/视图预览同时取帧 · 共享资源的**运行期互斥** · `CameraLease`（运行期独占租约，冲突拒绝启动）+ `CameraGrabGate`（per-camera 取帧串行化门）
- ③ 并行下界面要能分辨"这是哪条流程" · 可观测性 · 事件带 `FlowId/FlowName/Product`；日志结构化；右栏流程运行列表；视图标题条带流程名 + `[运行中]`
- ④ 高频并行结果 + 日志会淹没 UI 线程 · 投递限流 · 结果**覆盖式**投递（`Interlocked.Exchange`）已有先例；**日志改为批量队列 + 200 ms 拉取**，禁止逐条 `BeginInvoke`
- **决策 1：并行只做实例隔离，不动单链拓扑（`C-1` 不推翻）。**
- 已落地的 `FlowRunner.Begin/StepNext/Finish` 会话内核本身是**无状态驱动**的：会话对象 `FlowRunSession` 由调用方持有并传入，`FlowRunner` 只保有 `_algo` 与 `_autoRefs`。因此「并行」= 在**外层**给每条流程配一个 `FlowRunner` 实例 + 一个线程 + 一个会话，**`TryBuildChain` 与单链校验文案一行不改**。
- ✅ 这正是 PRD §3.3 假设 E 的结论，且与 `C-1` 完全一致。
- ❌ 不采用方案②（单流程内分支并行）：需重写拓扑解析、定义分支同步点、重新定义 `RunTransform` 作用域（分支各自修正还是共享？），与既有单链约束直接冲突，登记为 `FR-PAR-10`（P2）。
- **决策 2：`FlowRunner` 实例与流程严格 1:1，绝不复用。**
- 1. `_autoRefs`（位置修正 `RefSource=Auto` 的基准缓存，按节点 Id 存在执行器内存里）会**跨流程串号**——A 流程示教的基准会被 B 流程读到；
- 2. `VisionAlgo` 持有的原生句柄（`va_create`/`va_destroy`）**不是线程安全的**（模板状态、lastError 缓冲都在句柄里）；
- 3. 一条流程致命错误时要能单独 `Dispose` 它的上下文，共享实例做不到。

- **原生算法库** · **零改动**。`va_ocr_add_template` 已支持同标签多样本（`MatchAgainstTemplates` 对全部模板取 argmax，`labels[]` 为平行数组）；`va_ocr_template_count` 已够用。本期不需要新导出。
- **Q10 裁定** · **允许同标签多样本**，但机制只能是**同名不同扩展名（≤ 6 份）**——因为"文件名去扩展名即标签"这条加载规则是 C1/C4 的硬约束，任何 `A_001.png` 式后缀都会破坏它。详见 §2.4。
- **Q12 的真正难点** · `FlowModuleInfo.CreateDefaultParams()` 同时承担「新节点初始值」和「升级时缺键补齐值」两种语义。直接把默认值改成用户目录会**让极老配置在升级瞬间丢掉模板目录**（C1 违规）。本期把两者**拆成两个入口**（§3.2）。
- **UI-R11** · **已由 T01 交付**（`NodeParamField.DisabledReason` + 面板禁用渲染 + Schema 第 4 参）。**不立任务**，只留一条 T04 收尾动作（§2.1）。
- **结果区改版** · 弃用 `DataGridView`（无法做两行高可变行），改为 **`FlowLayoutPanel` + 每节点一个 `FlowResultRow` 控件**。不用 Graphics 自绘 → 无需进 `UiStyle` 三份白名单（§3.4）。
- **"主判据"从哪来** · **不能从图形反推**。新增结构化 `FlowNodeMetrics`，由各 `RunXxx` 在已有数值处顺手填；文案由 `NodeResultText` 一处生成、五处使用（§3.3）。
- **ROI 轮廓污染结果区** · 不止 Blob——`Filter`（606 行）与 `Measure`（1911 行）也塞。改为**辅助图形通道 `AuxShapes`**，一并解决三家（§3.5）。
- **空库状态** · `FlowNodeStatus` 现在**没有 `Warn`**，且 `StepNext` 会把 `Running` 一律改写成 `Ok/Ng`。要落地 Q19 必须加枚举值 + 加一条降级通道（§2.6 / §3.6）。
- **缩略帧（已定案）** · 连续运行**不缓存原帧**（5MP×5=100MB 会顶破 8h 红线），改为**每节点 1/4 缩略帧**（≈1.25MB），**按需生成**（点开该节点才登记抓帧）。只服务历史回看高亮；换算单向 `round(p/4)`；C5-e 断言框位误差 ≤2 缩略像素（§3.8 / §8.1）。
- **置灰参数的启用归属** · 五处必须在功能落地的同一包里解除：`RoiPick`/`RoiPreview`/`RoiAngle`/`FollowPose` → **T04**；`ShowStringBox` → **T07**。`RoiX/Y/W/H` **保持可用**（轴对齐裁剪本来就在工作），**不许一起灰**（§1.3）。
- **指纹 bug 归属** · 从 T09 **挪到 T08**——它与"改名/删除/迁移"是同一个功能面，必须同包交付；验收口径：改名 `A→B` 后**不重启软件直接运行，识别标签必须是 B**。
- **结果区粒度（已定案）** · **跟随选中节点：一次只显示"当前节点一行 + 该节点目标明细"**，不是全链常驻列表。全链概览由**画布节点卡片**（`UI-R06`/T07）承担，两块各司其职 —— 见 §10 R8。PRD v1.3 已同步（示意图与 `UI-R02` 均已改）。
- **任务分解** · **T06~T09 四个包 + T10 独立小包**（Q16 参数六组折叠），合计 25 个文件（新增 7 / 修改 18）。主线：**T06 ✅ → T08 → T10 → T04 → T07 → T09**；排序理由见 §7.3。

### 6.3 落地红线与踩坑

- §8.2 S1~S6 · §5.6「不再静默」清单 · v1.1（未再变）
- §8 表 C2 / C3、T08 红线 · 迁移 = 复制永不等于移动；源目录三样不变 · v1.1（未再变）
- 1 · **禁止型约束必须跟"为什么不能"** · 只写"不许"是呼吁，写清后果才是约束。例：不许合并老路径 → 否则 FR-06 逐像素一致立刻失效

- 模板读取失败**不判 NG**（跳过该文件） · **必须**逐个列出文件名 + 原因并计入失败计数（§8.2 S2），否则就是静默吞掉

- `RoiX / RoiY / RoiW / RoiH` · **保持可用** ← ★ 它们是真生效的（轴对齐裁剪已在工作） · 不置灰、**不归任何待启用项** · — · 不动
- **标签字节上限 7**：`VA_OCR_LABEL_BYTES = 8`，`va_ocr_add_template` 会把 label **静默截断**到 7 字节（`va_ocr.h:33`）。中文 3 字节/字 ⇒ **最多 2 个汉字**。若不校验，`华东区` 与 `华北区` 会被截成同一个标签而**静默合并**（比覆盖更难查）。→ `Encoding.UTF8.GetByteCount(label) <= 7`，否则拒绝并提示"标签过长（最多 2 个汉字或 7 个英文字符）"。
- **不静默覆盖**：`A.png` 已存在时，先比内容字节；相同 → "已存在相同样本，未重复添加"；不同 → 依次找下一个可用扩展名；6 个都占满 → "该字符已有 6 份样本，请先删除旧样本"。
- `Directory.CreateDirectory` 成功后**静默**（`1137`）→ 用户以为"目录自动建好了"，其实里面什么都没有；
- 2. **任何代码路径都不得把 `Warn` 当作 `Ng` 处理**。这句话是给未来的自己看的：`Warn` 是新增值，所有既有的"不是 Ok 就当失败"式写法（`status != Ok`、`status == Ng ? ... : ...` 的反面）都会**静默地**把 WARN 判成失败，而这类代码不会报错、只会在现场表现为"明明识别出来了却判 NG"。
- `UI-R08` 要"切回去还能看到结果"。若每节点缓存一帧 5MP **原图**（≈20MB），5 节点 = 100MB，**8 小时内存红线必挂**（PRD 5.3 末行）。
- **缩略帧的三条硬约束（★ 主理人明确要求，写死）**
- **★ 坐标换算方向与取整规则（必须有这条，否则会出现"框偏了一点、但看起来像摆放问题"的静默错误）**
- 反向（仅调试/断言用，禁止出现在业务路径）：p_full = p_thumb * Divisor
- **不预先取整**：`ThumbGeometry.ToThumb/ToThumbPoint/ToThumbRect` 保留浮点（`ThumbGeometry.Divisor = 4`），只在最终 `DrawRectangle/DrawLine` 落笔时由 GDI+ 取整。**禁止用 `(int)` 截断**——截断是单向的，会让所有框系统性偏左上 ≤1 缩略像素，看起来像"摆放问题"而不是"换算问题"；
- **反向换算一律禁止进入业务路径**：不得先算缩略坐标再乘回去，也不得在缩略图上做命中测试。命中/选中逻辑仍走 `ImageViewer` 的原图坐标系。
- **★ 缩略帧重建必须节流（rev4 补，T06 实现为每节点每 400ms 最多一次）**
- **★ 三态开关必须用 `int`，不能用 `bool`（rev4 补，T06 实测踩到）**

| 形状匹配粗层走梯度方向响应图查表（`kDirBins=32`，旋转 = 档位整体平移）+ `cv::integral` 剪枝；**最细层必须精确 `atan2` + 双线性** | 细层也量化会引入 ≤0.01 系统偏差 | `src/algo/algo_shape.cpp` |
| `cv::phase(gx, gy, ang, angleInDegrees)` 第 4 参传 `false` 返回**弧度** | 按「度→档位」换算会全落档位 0，表现是全部 0 命中、最佳候选贴边、得分约 0.4 | `src/algo/algo_shape.cpp` |
| 查表有工作量门槛 `kFastPathMinWork`（`nPos*nPoses`）；诊断 `VA_SHAPE_DEBUG=1` / `VA_SHAPE_PRECISE=1` | 小搜索摊不回方向图+积分图的一次性开销（38.5ms→41.8ms） | `src/algo/algo_shape.cpp` |
| 控件库零第三方依赖（纯 GDI+）；OpenCV 用 `IntPtr + stride` | `Bitmap(24bppRgb)` 的 Stride 是 4 字节对齐 ≠ width*3 | `VisionSystem.Controls` |
| **坐标约定**：几何属性用图像坐标；`LineWidth`/`HandleSize`/命中容差用屏幕像素；换算 `control = image*Zoom + Offset` | 混用会偏移 | `Controls/Geometry/*` |
| `IGeometryShape` 接口**没有 `Label`**：只有 `RectangleShape`/`RotatedRectShape` 有；`OcrChar.X/Y/W/H` 是 **double** | 类型假设会编译失败 | `Controls/Geometry` |
| 改图形几何属性不自动重绘 → `Shapes.NotifyChanged()`；集合增删改会自动重绘 | 画面不刷新 | `Controls/Geometry/ShapeCollection.cs` |
| VS 文件夹层级由 `.vcxproj.filters` 决定，不是磁盘目录；新增 .h/.cpp 要同时改 `.vcxproj` 与 `.filters`；C# 项目不需要 filters | 解决方案里文件平铺在根目录 | `src/VisionAlgo.Native/*.vcxproj*` |
| 用 C++17 须在 `ClCompile` 加 `LanguageStandard=stdcpp17`；bat 必须纯 ASCII | GBK 代码页下中文 bat 会解析失败 | `VisionAlgo.Native.vcxproj`、`build.bat` |
| 相机 `va_camera_*` → `NativeCamera.cs` → `LocalCamera.cs`，句柄独立于算法 Context；Id 前缀 `USB-`/`SIM`/`HIK` | 上下文混淆 | `Native/NativeCamera.cs`、`Camera/LocalCamera.cs` |
| `cv::VideoCapture::read` 阻塞无超时 → 关相机用后台线程延迟释放；释放原生上下文前必须 Join 运行线程 | 卡死/崩溃 | `Camera/LocalCamera.cs` |

### 7.6 构建与验证

| 规则 | 为什么 | 权威位置 |
|---|---|---|
| 构建走根目录 `build.bat`（Debug / Release 各跑一次）；命令行直接调构建工具会被本机策略拦 | 环境约束 | `build.bat` |
| 改 C++/C# 要 Debug + Release 各跑一次；只改 md 不必 build | 配置差异（优化开关曾漏设） | 项目约定 |
| 三个 Smoke 工程不入库（`.gitignore`），已从 `VisionSystem.sln` 移除，本机统一用 `_build_smoke.bat` 构建 | clone 后不提示缺项目 | `.gitignore`、`_build_smoke.bat` |
| 跑 Smoke 前必须保证原生 DLL 在输出目录：`SmokeUi.csproj` 有 PostBuildEvent，`_build_smoke.bat` 给 SmokeAlgo 补 xcopy | 漏了会报「找不到入口点」这类与代码无关的假失败 | `SmokeUi.csproj`、`_build_smoke.bat` |
| Release 下形状匹配训练可能 <1ms → 用 `RetrainSuffix(bool retrained, int ms)` 而不是 `ms>0` 判断 | 「重训过」与「没重训」必须在摘要上可区分 | `Flow/NodeResultText.cs` |

| 下结论前重新核对文件与 csproj；不要用 `&&` 串联独立检查；「控件点了没反应」先查 Designer 漏 `Controls.Add` | 团队教训 | 项目约定 |
